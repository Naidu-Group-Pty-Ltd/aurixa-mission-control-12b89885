# Repository audit — August 2026

A whole-repository audit of Aurixa Mission Control, beyond the clone/handoff
pipeline that earlier work covered. 783 files, ~141k lines of TypeScript, 168
migrations, 141 routes, 46 public API routes.

This is the record of what was looked at, what was found, what was changed and
what is left. Where something was checked and found sound, that is written down
too — an audit that only lists problems cannot tell you what it covered.

---

## The finding that produced most of the others

`tsconfig.json` had `"strict": false`, and 164 files carried a bare
`// @ts-nocheck` — 50 of them in `src/server`. Between them they were hiding
**1,038 type errors**, and they were also **161 of the repository's 162 lint
errors**, so `npm run lint` exited 1 and _no pull request could pass the repo's
own CI_.

The reason the count was so large is a single mechanical fact rather than 164
decisions. TanStack's `ServerFnBuilder` starts with `TMiddlewares = undefined`,
and `AppendMiddlewares` asks `undefined extends ReadonlyArray<any>`. With
`strictNullChecks` off that question answers **true**, so
`.middleware([requireSupabaseAuth])` inferred `readonly [...any[], M]`;
`AssignAllMiddleware` cannot walk a tuple with a leading rest element and falls
back to its accumulator; and every server function's `context` was therefore
typed `undefined`. That accounted for **679 of the 1,038**.

Turning `strictNullChecks` ON therefore _removes_ errors here. It is load-bearing
for the framework's inference, not merely a null-safety preference, and there is
a note beside the flag saying so.

The second bulk cause: six tables — `user_invites` and the five
support/remediation tables — were missing from the generated Supabase types.
`supabase-js` resolves `.from("x")` against the `Database` type and a table it
does not name resolves to `never`, so every column read, insert payload and
filter on those tables silently stopped being checked. That was another ~120.

**Result: 1,038 errors across 140 files → 97 across 30.**

## Defects found underneath, all fatal or silently wrong at runtime

Every one of these was in a file under `@ts-nocheck`, and every one reported as
normal operation.

### Names the database does not have

degraded row — they failed outright.

| What                                                                                                        | Effect                                                                                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

The parity-refresh cron had the test inverted: `latest` came back null, so every handoff looked stale and it recomputed parity for the whole fleet on every run. |

| `feedback_pending_forward` RPC missing from the generated types                                             | An undeclared RPC is unchecked in both directions, and a name that does not exist answers 404 — which `retryPendingForwards` reads as `!Array.isArray(data)` and reports as an empty backlog.                                                                                                           |

### Enum values that were never declared

`notification_kind` rejects an unknown value outright, and all three inserts
discarded the error, so the notification simply never arrived:

- `handoff_consent_received` — **nobody in Mission Control has ever been told
  that a client submitted their Supabase org details, PAT and signed DPA.**
- `github_app_access_drift`
- `api_usage_settlement_failed`

### The stored client PAT was unreadable no matter which path wrote it

`client_supabase_accounts.pat_ciphertext` is `BYTEA`, and the repository had
three incompatible answers for getting a string into it:

- `/api/public/handoffs/consent` wrote the bare `enc:v1:…` string. Postgres
  stored those bytes but returns them as `\x656e633a…`, so `decryptSecret` saw
  no prefix, returned the hex untouched, and the caller used **that** as the PAT.
- `client-supabase-accounts.functions.ts` wrote a Node `Buffer`, which
  supabase-js JSON-encodes as `{"type":"Buffer","data":[…]}` — not a bytea
  literal at all — and discarded the error, leaving an account that _looks_
  captured with no credential behind it.
- Every read did `String(...)`, correct for neither.

`encodeBytea` / `decodeBytea` in `crypto.server.ts` are now the single answer at
all eleven sites. `decodeBytea` passes plain text through, so a legacy row still
resolves. Seven tests pin the round trip with encryption both off and on.

### Smaller, still real

- `cfFleetAnalytics` typed one branch's `analytics` as a bare `[]`, i.e.
  `never[]`. Unioned with the populated branch, every consumer got an element
  type of `never` — which is why the Cloudflare fleet page could not read
  `a.clone_id` off its own data.
- `AuditShipperCard` called `confirm({ title, description, … })` without
  `useConfirm()` in scope, so it resolved to the DOM's `confirm(message: string)`:
  the HMAC rotation prompt read **"[object Object]"** and still returned a
  boolean, so the rotation went ahead.
- The handoff detail page's GitHub App card reads `h.clones?.github_owner`, but
  the embedded select only fetched `id, name, slug` — it printed "the clone/repo"
  every time.
- `security.scans.tsx` read `d.job.repo_full_name` where `d.job` is nullable.
- `runBrandSync` spread `...result` _after_ the `ok`/`error` it had just
  computed, so both were dead.
- Two `return { ok: true as const, ...result }` — `result` carries its own `ok`,
  which wins, so the annotation claimed something the runtime never did.
- `/api/public/tokens/balance` asked PostgREST for `clone_id = NULL` for
  platform-level keys. No row satisfies that, so the empty add-on list was right
  by accident.
- `/api/public/usage/report` could not express a platform-level key at all.

## Security

### `/api/health` named missing secrets to anonymous callers

The endpoint is unauthenticated on purpose — the thing asking is usually a
monitor holding no credential — which makes _what it says_ a security question.
It answered `"missing: SUPABASE_SERVICE_ROLE_KEY, STRIPE_SECRET_KEY, …"` to
anybody: the platform's credential inventory plus which ones are absent right
now. The shape is now identical for everyone and the detail is gated on the cron
credential. The database check reports `database_unavailable` rather than the
driver's message, which can carry a relation, column or role name.

### `encryptSecret` is a no-op without `CREDENTIALS_ENC_KEY`, and nothing said so

It does not warn and it does not fail; the columns are still called
`..._ciphertext` and `..._enc`. Unset, these sit in **plaintext** in Mission
Control's own database:

- every managed clone's Supabase **service-role key** and **database password**
- client Supabase **personal access tokens**
- queued clone **admin passwords**
- per-clone **Stripe webhook secrets**

`isEncryptionEnabled()` existed and had no caller outside its own test, so no
deployment could report which state it was in. `/api/health` now carries
`checks.credential_encryption`, and `.env.example` names what the key actually
protects instead of describing plaintext as "the previous behavior".

That check is deliberately excluded from the endpoint's `ok`: it is a
misconfiguration for a person to fix, not an outage for a load balancer to route
around, and no restart changes it.

### Two public routes minted Stripe sessions with no rate limit

`/api/public/storefront/checkout` and `/api/public/storefront/setup` create a
Stripe Checkout Session, and may create a Customer, per accepted request. Both
accept a `uid` — which the route's own doc comment calls "the operator-assigned,
**stable** billing_user_id", i.e. deliberately not a secret, carried in a
pricing-page link. Every sibling family (`tokens.*`, `seats.*`, `billing.*`)
already called `checkRateLimit`; the storefront family was the exception, and it
is the one family reachable with no secret at all. Both now limit on the
credential at 12/minute.

### Dependency advisories: 19 → 0

1 critical, 9 high, 8 moderate, 1 low → **zero**.

- `vitest` 2.1.9 → 4.1.11 clears the critical (`GHSA-5xrq-8626-4rwp`, CVSS 9.8)
  and the vite/esbuild/vite-node chain beneath it. All 807 tests pass unchanged
  on v4; only the `--reporter=basic` CLI flag is gone, which the `test` script
  never used.
- `undici` pinned to `^7.29.0`. It is reached through `nitro`, the **production**
  server runtime, and versions `7.0.0–7.28.0` carry five advisories including a
  TLS certificate validation bypass. nitro accepts the patched version, so the
  pin does not force a major.
- `esbuild` pinned to `^0.28.1`; only `tsx` pulled a vulnerable copy.

### October 2026: 20 → 0 again

7 critical, 12 high, 1 moderate had accumulated by 17 Oct 2026. The criticals
and the highs with an in-range release went first (TanStack Start's XSS,
seroval, shell-quote); the nine that were left are cleared here, with
`npm audit` at **zero**.

- **The nitro beta chain** (nitro, env-runner, miniflare, sharp, undici,
  wrangler, `@cloudflare/vite-plugin`, and Lovable's preset through nitro):
  `nitro` 3.0.260603-beta → 3.0.260903-beta, whose env-runner 0.2 no longer
  carries miniflare 4 (which pins sharp 0.35.2 and undici 7.28.0), and
  `@cloudflare/vite-plugin` ^1.25.5 → ^1.64.0, whose wrangler 4.151 and
  miniflare 5 pin sharp 0.35.5 and undici 7.29.1. The `undici` floor rises to
  `^7.29.1` for the ten advisories fixed there.
  - `nitro` is also in `overrides`, as `$nitro`. Lovable's preset declares the
    optional peer `nitro >=3.0.260603-beta`, and under semver's prerelease rules
    no later beta satisfies it, so npm refused every install. The preset itself
    compares the numbers and is content.
  - The new nitro reads `wrangler.jsonc` without trailing commas, and the one
    after `main` failed the build; it is gone.
  - Verified: production build, `wrangler dev` on the built Worker (pages and
    hooks answer under workerd), and both lockfiles hold one copy of each
    package at the fixed version.
- **`node-forge`**, which has no fixed release, is removed. It only rewrapped
  the GitHub App's PKCS#1 key as PKCS#8, and that is a wrap of the DER, not a
  cryptographic operation: `src/lib/rsa-key-pem.ts` does it in plain code, held
  byte-for-byte to Node's own PKCS#8 output at 1024, 2048 and 4096 bits, and
  shown to sign an App JWT that verifies — in Node and inside workerd. The PEM
  helper on the auth page checks keys with WebCrypto instead.

### Checked and found sound

- **Server-function authorization.** All 405 `createServerFn` occurrences.
  Ten have no guard in the chain; each was read individually and each is
  deliberately public and documented (handoff-token checkout lookups, public
  pricing, VAPID public key, invite validation/acceptance).
- **Public route authentication.** All 46 `api.public.*` routes. Both Stripe
  webhooks verify signatures and claim events atomically before doing any work,
  answering 5xx on a claim failure so Stripe retries. Support ingest requires an
  HMAC signature or a shared secret. Storefront routes are scoped by a
  single-use handoff token or a `uid`. `/hooks/*` all require the cron secret.
- **Row Level Security.** All 149 tables have RLS enabled; 147 carry policies.
  The two that do not — `billing_handoffs` and `support_ingest_requests` — are
  reached only by the service-role client, which is the correct closed state.
- **Constant-time comparison.** `timingSafeEqualStr` checks length, then
  `crypto.timingSafeEqual`.
- **Secret logging.** No code path logs a secret value.

## Guards added

Each of these looks for a failure that produces **no runtime signal** — which is
why they are CI steps rather than notes. All three were checked against a
deliberately reintroduced regression.

| Script                        | Catches                                                                                                                                                                                                                                          |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `check-supabase-types.mjs`    | A table, enum, enum value or `.rpc()` name in the migrations that the generated types do not declare. A missing table makes every query against it `never`, so `tsc` passes _because_ nothing is checked. Runs before the typecheck it protects. |
| `check-ts-nocheck-budget.mjs` | A new `@ts-nocheck`. The set of 30 files still allowed one is frozen; the check fails both when a file is added and when one is fixed without updating the ledger, so the number can only go down.                                               |
| `check-rls-policies.mjs`      | A table with RLS on and no policy, or one dropping off the service-role-only list. Nothing at runtime reports this: RLS filters rows rather than failing requests, so a closed table reads as an empty list.                                     |

### Duplicated helpers, consolidated

Three helpers existed as byte-identical copies. Each is now in one place:

- `mapWithConcurrency` → `src/lib/concurrency.ts`, deliberately pure so both a
  `.server.ts` module and a client-reachable `.functions.ts` can import it
  without dragging server code into a browser bundle. Tested for order
  preservation under out-of-order completion, the concurrency ceiling, the
  runner count and the empty case.
- `timingSafeEqualStr` → exported from `cron-auth.server.ts`. A comparison that
  has to be constant-time is exactly the kind of thing that should not exist
  twice.
- `writeAudit` / `notify` → `src/server/audit.server.ts` as `writeAuditLog` and
  `notifyOperators`, which additionally **log** a failed write. Both tables
  exist so a person can find out what the platform did, and both were written
  with the result dropped — so the one failure that matters was the one nothing
  reported. They still do not throw: an audit write must not take down the
  operation it is recording, but "best effort" and "silent" are different
  things.

`ban-ts-comment` now requires a description, and each of the 30 remaining files
states at its top how many errors it holds down and of what kind — so removing
one is a scoped job rather than an open-ended offer.

CI installs with `npm ci` rather than `npm install`. The comment it replaced said
the lockfile lagged the manifest; that was no longer true, and `npm ci` fails
loudly on drift instead of quietly installing a tree nobody tested. It earned
its keep immediately: it caught a lockfile desync that `npm audit fix` had
introduced during this audit.

## Second pass — scheduling, indexes and batch fairness

A later sweep over dimensions the first pass did not touch: scheduled-job
coverage, database physical design, batch behaviour, retention, CORS, input
validation and money-path concurrency.

### Six workers that nothing has ever called

Each of these opens its own file by stating the cron cadence that schedules it,
and none of the six appears in any migration, any GitHub workflow, or any host
cron config:

| Route                              | What it says about itself                   |
| ---------------------------------- | ------------------------------------------- |
| `hooks/edge-drain`                 | "Called by pg_cron every minute"            |
| `hooks/edge-drift`                 | "Daily edge drift check"                    |
| `hooks/handoff-observability-poll` | "pg_cron POSTs here every 15 minutes"       |
| `hooks/handoff-parity-refresh`     | "Cron-invoked … older than 6 hours"         |
| `hooks/drift-refresh`              | "pg_cron schedules a POST here every 5 min" |
| `hooks/api-usage-settle`           | "Cron-invoked settlement … Daily is enough" |

`hooks/run-schedules` is not a general dispatcher — it walks `cascade_schedules`
rows and nothing else. `api-usage-settle` is the one that costs money: it closes
every ended billing period and pushes what it owes onto the tenant's next Stripe
invoice. `edge_provisioning_jobs` has had no drainer at all.

Nothing could have reported this. There is no failing request to log, because
there is no request. `scripts/check-cron-coverage.mjs` now requires every
`/hooks/*` route to be scheduled in a migration or declared event-driven.

### `/hooks/brand-drift` fired twice every 30 minutes

Scheduled under two job names — `brand-drift-30min` (20260607) and
`aurixa-brand-drift-scan` (20260609) — both `*/30`, same URL, neither
unscheduling the other.

### 35 foreign keys a parent delete had to scan

Postgres indexes the referenced side of a foreign key and never the referencing
side, so every `ON DELETE CASCADE` / `SET NULL` sequentially scans the child.
88 FK columns had no leading index; 68 carry a referential action; 35 of those
are also filtered on directly in application code, so the same missing index
cost twice. Those 35 are indexed; the rest are deliberately left alone.

Worth recording how that number was reached, because the first attempt was
wrong: a regex over `REFERENCES` ran past a `CREATE TABLE` boundary in a file
that puts several columns on one line, invented two columns on
`api_provider_rates` that do not exist, and missed indexes in forms it did not
anticipate. The figures above come from the migrations' parse tree (pglast),
and every target was then checked against the generated types.

### Batches that processed an arbitrary subset

Seven queries capped their batch with no `ORDER BY`. An unordered `LIMIT`
returns an arbitrary subset, so above the cap the same rows can be picked every
run while others starve indefinitely — silently, since a truncated batch looks
exactly like a small one.

The serious one was not a worker. `tenantsWithLedgerActivity` answered a
membership question — _which of these tenants have ledger activity_ — with a
single `.in(…).limit(1000)` over `token_ledger`, a table with no retention.
Once a busy tenant's rows filled the cap the others came back absent, and absent
there means "no activity", which is the decisive signal for **which tenant a
clone bills to**. It now probes each candidate with `limit(1)`; this path only
runs when one clone has several tenants, so the list is a handful.

The other six are ordered oldest-first so a backlog drains rather than starves,
their caps are named constants, and the two that return a summary report
`truncated` when the batch comes back full.

### `support_ingest_requests` grew without bound

One row per support-portal ingest request, never deleted, while the limiter that
owns the table runs three `count(*) exact` queries over it per request. It gets
slower as it grows, and its error path is `catch → limited: false` — it fails
OPEN by design. Unbounded growth therefore ends with the rate limit quietly not
being enforced on a public endpoint. Its sibling `token_api_rate_limits` has
been purged at 14 days since it was created; this one is now purged at 7.

### Nothing could tell whether cron ever delivered

pg_cron records whether the SQL it ran succeeded. Every scheduled job here runs
exactly one statement — `SELECT net.http_post(...)` — which succeeds by
_queueing_ a request and returns a request id, not a response. So
`cron.job_run_details` reads "succeeded" whether the endpoint answered 200, 401,
404, or never answered at all.

Nothing in this repository had ever read `cron.job_run_details` or
`net._http_response`. There was no way to answer "is cron actually reaching us"
— the question that matters after a domain change, a rotated `CRON_SECRET`, or a
job whose URL was wrong from the start. Both catalogs live in schemas PostgREST
does not expose.

`public.cron_delivery_health()` joins them and returns one row per job: when it
last ran, what pg_cron thought, and what the HTTP call actually came back with.
`/api/health` reports failures from it under the same credential gate as the
secret names — which of your workers is failing, and how, is not an anonymous
caller's business. `delivered` is deliberately three-valued: null when no
response was matched, because "we do not know" and "it failed" are different
answers and only one of them is alarming.

Verified by execution against a real PostgreSQL 16 with seeded catalogs,
including the case that was invisible before: pg_cron reporting `succeeded`
while the HTTP call came back 401.

### Checked and found sound (second pass)

- **Money-path concurrency.** `reserve_tokens` takes `pg_advisory_xact_lock` on
  the tenant, is keyed by idempotency key, and already uses `IS NOT DISTINCT
FROM` for the NULL-clone case. `commit_tokens`, `apply_topup`, `reserve_seat`
  and `commit_seat` are all SQL functions rather than check-then-act in
  TypeScript.
- **CORS.** `Access-Control-Allow-Origin: *` on the storefront routes, with no
  credentials and token-based authorisation — correct, and documented as such.
- **Input validation.** Four public routes parse JSON without zod; all four
  validate by hand and adequately.
- **Unbounded reads.** Eight `SELECT`s against growth tables looked uncapped;
  all eight are bounded by a parent-id or time filter.
- **Dead components.** None — every component in `src/components` is imported.
- **`updated_at` triggers.** Nine tables have the column without a trigger;
  nothing reads `updated_at` on any of them, so it is cosmetic.
- **Retention.** 16 tables are purged on a schedule. Of the rest, `token_ledger`
  and `feedback_submissions` are records that should not expire.

## What is left

**97 type errors across 30 files**, listed in `scripts/ts-nocheck-budget.txt`
with a per-file count and error-kind breakdown. They are mechanical — `Json`
assignability on jsonb columns, nullability, a few server-function context
unions. No wrong-column or undeclared-enum errors remain in that set; that class
was cleared.

**30 of 57 `const admin = supabaseAdmin as any` aliases remain.** 27 were
removed — every one where the cast turned out to be unnecessary once the six
missing tables were declared. Removing the other 30 costs roughly 73 further
type errors of the same mechanical kind, measured rather than estimated.

**412 of 886 Supabase result destructures discard the `error`** (46%), and there
are 549 fire-and-forget writes with no destructure and no `.catch`. This is the
pattern behind nearly every defect above: a read that failed is indistinguishable
from a row that is absent. Most of the 549 are `audit_log` and `notifications`
inserts, which are best-effort by intent — but an audit record silently lost is
material for a compliance product, and it is exactly what stopped anyone noticing
that three notification kinds had never been valid. Worth a shared helper that
logs rather than 961 individual edits.

**Three lockfiles.** `bun.lock` and `bun.lockb` sit alongside `package-lock.json`.
No workflow uses them and `bun.lockb` predates the support-ticketing dependencies
by three weeks, so `bun install` produces a tree missing packages the app now
imports. Left in place because the generating platform's own toolchain could not
be verified from this environment — a decision for whoever owns that pipeline.
